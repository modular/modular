A
[`TileTensor`](/api/mojo/layout/tile_tensor/TileTensor/)
provides a view of multi-dimensional data stored in a linear array.
`TileTensor` abstracts the logical organization of multi-dimensional data from
its actual arrangement in memory. You can generate new tensor "views" of the
same data without copying the underlying data. This facilitates essential
patterns for writing performant computational algorithms, such as:

- Extracting tiles (sub-tensors) from existing tensors. This is especially
  valuable on the GPU, allowing a thread block to load a tile into shared
  memory, for faster access and more efficient caching.
- Vectorizing tensors—reorganizing them into multi-element vectors for more
  performant memory loads and stores.
- Partitioning a tensor into thread-local fragments to distribute work across a
  thread block.

`TileTensor` is especially valuable for writing GPU kernels, and a number of
its APIs are GPU-specific. However, `TileTensor` can also be used for
CPU-based algorithms.

A `TileTensor` consists of three main properties:

- A [layout](/tile-tensor/layouts/), defining how the elements are
  laid out in memory.
- A `DType`, defining the data type stored in the tensor.
- A storage handle whose representation is determined by its engine.

Figure 1 shows a 2D column-major layout, and the corresponding linear array of
storage. The values shown inside the layout are offsets into the storage: so the
coordinates (0, 1) correspond to offset 2 in the storage.

Because `TileTensor` is a view, creating a new tensor based on an existing
tensor doesn't require copying the underlying data. So you can easily create a
new view, representing a tile (sub-tensor), or accessing the elements in a
different order. These views all access the same data, so changing the stored
data in one view changes the data seen by all of the views.

A tensor's storage engine determines how its elements are represented. With
`DefaultEngine`, an element is a scalar or a SIMD vector, depending on the
engine's element width. The tensor borrows its storage; creating another view
doesn't extend the owner's lifetime.

The code snippets are illustrative fragments, not standalone programs. Indexing
snippets assume an existing tensor and coordinates; GPU snippets assume the
corresponding GPU and layout imports and a device context. Comments mark omitted
application-specific processing, not implementations supplied by this guide.

## Accessing tensor elements

For a `TileTensor` with a simple row-major or column-major layout, you can
address the tensor like a multidimensional array to access elements:

```mojo
var element = tensor2d[x, y]
tensor2d[x, y] = z
```

For multi-axis indexing, pass coordinates matching the tensor's layout. For
simple layouts, the number of coordinates is the layout's *rank*: two for a 2D
tensor, three for a 3D tensor, and so on. `TileTensor` also accepts a single
logical index, which the layout maps across its dimensions.
When a function takes a generic `TileTensor`, use a compile-time assertion to
establish the rank before multi-axis indexing. These compile-time checks don't
verify that the index values are in bounds.

```mojo
from layout import TileTensor


def read_element(tensor2d: TileTensor, x: Int, y: Int):
    comptime assert tensor2d.flat_rank == 2
    var element = tensor2d[x, y]
    var linear_element = tensor2d[x]  # A single logical index.
```

For more complicated "nested" layouts, such as tiled layouts, the
number of indices **doesn't** match the rank of the tensor. For details, see
[Tensor indexing and nested layouts](#tensor-indexing-and-nested-layouts).

The `__getitem__()` method returns a SIMD vector whose width is the tensor's
`element_size`, determined by its storage engine. In a generic function, the
compiler needs evidence that this width is 1 before converting the result to a
scalar type such as `Int`. For example:

```mojo
from layout import DefaultEngine, TileTensor


def read_scalar_index(
    tensor: TileTensor[.int32, Engine=DefaultEngine[element_width=1], ...]
) -> Int:
    comptime assert tensor.flat_rank == 2
    return Int(tensor[0, 0])
```

If the width is greater than 1, a vector can't be converted directly to an
`Int`. This parameter type restricts the example to non-vectorized default
storage, making the requirement explicit for callers.

To select a scalar explicitly, take the first lane of the returned SIMD
vector. For a vectorized view, this selects only the first lane, not the whole
element:

```mojo
var element = tensor[row, col][0]  # Select the first lane.
```

You can also access elements using the `load()` and `store()` methods, which
let you specify the vector width explicitly:

```mojo
var elements = tensor.load[width=4]((row, col))
elements = elements * 2
tensor.store[width=4]((row, col), elements)
```

These methods take a `Coord`, which a tuple can supply implicitly. A width-4
access reads or writes four consecutive scalar values starting at the mapped
offset. Ensure that those values are in bounds and satisfy the requested
alignment; the methods don't clip the access to the layout's dimensions.

### Tensor indexing and nested layouts

A tensor's layout may have nested modes (or sub-layouts), as described in
[Introduction to layouts](/tile-tensor/layouts/). These layouts
have one or more of their dimensions divided into sub-layouts. For example,
Figure 2 shows a tensor with a nested layout:

<figure>

![](../images/layout/tensors/layout-tensor-indexing-nested.png#light)
![](../images/layout/tensors/layout-tensor-indexing-nested-dark.png#dark)

<figcaption><b>Figure 2.</b> Tensor with nested layout</figcaption>

</figure>

Figure 2 shows a tensor with a tile-major nested layout. Instead of being
addressed with a single coordinate on each axis, it has a pair of coordinates
per axis. For example, the coordinates `((1, 0), (0, 1))` map to the offset 6.

With `TileTensor`, you can pass nested coordinates to the subscript operator
as a `Coord`, or pass a flattened version of the coordinates. For example:

```mojo
from layout import Coord

# Retrieve the value at ((1, 0), (0, 1)).
var nested_element = nested_tensor[Coord(Coord(1, 0), Coord(0, 1))][0]
var element = nested_tensor[1, 0, 0, 1][0]
```

When passing separate coordinates for every sub-mode, the number of indices
must match the *flattened rank* of the tensor.

`TileTensor.load()` and `TileTensor.store()` also accept nested `Coord` values.
Use coordinates that match the nested structure, or flatten every sub-mode
when using separate subscript arguments.

## Creating tensors {#creating-a-layouttensor}

There are several ways to create a tensor, depending on where its data resides:

- On the CPU.
- In GPU global memory.
- In GPU shared or local memory.

The constructors borrow existing storage. Methods such as `tile()` produce
additional views of the same storage.

:::note No bounds checking

The tensor constructors don't do any bounds-checking to verify
that the allocated memory is large enough to hold all of the elements specified
in the layout. It's up to the user to ensure that the proper amount of space is
allocated.

:::

### Creating a `TileTensor` on the CPU {#creating-a-layouttensor-on-the-cpu}

While `TileTensor` is often used on the GPU, you can also use it to create
tensors for use on the CPU.

To create a `TileTensor` for use on the CPU, you need a native
[`TensorLayout`](/api/mojo/layout/tile_layout/TensorLayout/) and storage for the
tensor data. Use `row_major()` to build a static native layout and an
[`Array`](https://mojolang.org/docs/std/collections/array/Array/):

```mojo
from std.collections import Array
from layout import TileTensor, row_major

comptime rows = 8
comptime columns = 16
comptime layout = row_major[rows, columns]()
var storage = Array[Float32, rows * columns](uninitialized=True)
var tensor = TileTensor(storage, layout).fill(0)
```

`Array` is a statically-sized, stack-allocated array, so it's a fast and
efficient way to allocate storage for small tensors. There are
target-dependent limits on how much memory can be allocated this way, however.
The constructor accepts a `Span`; an `Array` converts to a span implicitly.
Keep the storage alive for as long as any tensor view uses it.

You can also create a `TileTensor` using a
[`Pointer`](https://mojolang.org/docs/std/memory/pointer/Pointer/). This may be
preferable for very large tensors.

```mojo
from std.memory import Layout as MemoryLayout, alloc, dealloc, unsafe_memset
from layout import TileTensor, row_major

comptime rows = 1024
comptime columns = 1024
comptime buf_size = rows * columns
comptime layout = row_major[rows, columns]()
var allocation = alloc(MemoryLayout[Float32](count=buf_size))
var ptr = allocation.unsafe_ptr()
unsafe_memset(ptr, 0, buf_size)
var tensor = TileTensor(ptr, layout)
tensor[0, 0] = 1
print(tensor[0, 0])
dealloc(allocation^)
```

Note that this example uses
[`unsafe_memset()`](https://mojolang.org/docs/std/memory/memory/unsafe_memset/)
instead of the tensor's `fill()` method. The `fill()` method performs
elementwise initialization of the tensor, so it may be slow for large tensors.
The allocation owns the memory; the tensor only borrows it. Release the
allocation after the last use of every view, and don't access those views after
deallocation.

### Creating a tensor on the GPU {#creating-a-layouttensor-on-the-gpu}

Allocate GPU global memory from the host with
[`DeviceContext.enqueue_create_buffer()`](/api/mojo/max/gpu/host/device_context/DeviceContext/#enqueue_create_buffer).
Construct a `TileTensor` from the resulting `DeviceBuffer` and a native layout.
The view can be passed to `enqueue_function()`, but its device memory must not
be dereferenced on the host. Initialize or retrieve data with the device
context's copy operations and synchronize before reading copied host data.

For a complete GPU initialization function, see
[Creating a TileTensor in global memory](/tile-tensor/tensors/#creating-a-tiletensor-in-global-memory).

Inside a GPU kernel, use the module-level
[`stack_allocation()`](/api/mojo/layout/tile_tensor/stack_allocation/) function
for statically sized shared or local storage. For example, this fragment
allocates a 16-by-16 shared tensor:

```mojo
from layout import row_major, stack_allocation

var shared_tile = stack_allocation[DType.float32, address_space=.SHARED](
    row_major[16, 16]()
)
```

Shared storage is visible to the threads in a block. Local storage is private
to a thread. The allocation does not escape the function that creates it.
Synchronize threads before reading values written by other threads.

## Tiling tensors

[`tile()`](/api/mojo/layout/tile_tensor/TileTensor/#tile) creates a sub-tensor
view. Tile coordinates select positions in the grid of tiles, not individual
elements. This fragment creates a 64-by-128 tensor and selects the 32-by-32
tile at row 0, column 1:

```mojo
from std.collections import Array
from layout import TileTensor, row_major

var storage = Array[Float32, 64 * 128](fill=0.0)
var tensor = TileTensor(storage, row_major[64, 128]())
var tile = tensor.tile[32, 32](0, 1)
```

The tile borrows the same storage and retains the parent's strides. Changing
`tile[0, 0]` changes `tensor[0, 32]`.

For nested layouts, tile extraction selects outer coordinates and retains the
inner modes' strides. Choose tile sizes consistent with the layout's inner
modes; see [Using TileTensor](/tile-tensor/tensors/) for nested examples.

### Iterating over tiles

Use ordinary loops to select tiles. This fragment assumes `tensor` is the
64-by-128 tensor above:

```mojo
for tile_row in range(2):
    for tile_col in range(4):
        var tile = tensor.tile[32, 32](tile_row, tile_col)
        tile[0, 0] = 1
```

### Handling tensor boundaries

TileTensor does not automatically clip a tile's shape at the edge of its parent.
A tile view can describe addresses outside the backing allocation. Only access
coordinates whose mapped addresses are valid. For an incomplete edge tile,
check the corresponding parent coordinates before loading or storing, or use
an explicitly predicated copy operation suited to your kernel.

Do not assume that the legacy masked-tile or tiled-iterator APIs have native
TileTensor equivalents. The loop above uses only complete, in-bounds tiles.

## Vectorizing tensors

[`vectorize()`](/api/mojo/layout/tile_tensor/TileTensor/#vectorize) groups
scalar storage into vector elements without copying it. Its compile-time
arguments specify a vector shape, one size per layout dimension. For a
statically laid-out 2D row-major tensor, this fragment groups four neighboring
columns into each vector element:

```mojo
var vectorized_tensor = tensor.vectorize[1, 4]()
```

The layout and engine must support this view. Ensure that the mapped storage,
vector width, and alignment meet the requirements of subsequent accesses.
A vectorized view does not allocate storage or make an out-of-bounds vector
access safe. Use `load[width=...]()` and `store[width=...]()` when you need an
explicit vector access without changing the view's element width.

## Partitioning a tensor across threads

[`distribute()`](/api/mojo/layout/tile_tensor/TileTensor/#distribute) selects a
thread-local fragment using a thread layout and a thread identifier. This kernel
fragment assumes `tile` is a static 16-by-16 row-major tile and partitions it
over a warp:

```mojo
from max.gpu import WARP_SIZE, lane_id
from layout import row_major

comptime simd_size = 4
comptime thread_layout = row_major[WARP_SIZE // simd_size, simd_size]()
var fragment = tile.vectorize[1, simd_size]().distribute[thread_layout](
    lane_id()
)
```

This fragment assumes the tile's dimensions and strides are known at compile
time and satisfy the distribution constraints. Each lane's fragment borrows the
original storage; the operation does not move data between threads.

## Copying tensors

[`copy_from()`](/api/mojo/layout/tile_tensor/TileTensor/#copy_from) copies
values from another tensor into a mutable destination. Both shapes must be
statically known and have the same total element count. Layouts determine the
source and destination addresses, so the views need not use the same memory
order. When multiple threads cooperate, partition their work so that they do not
write the same destination elements concurrently.

[`copy_from_async()`](/api/mojo/layout/tile_tensor/TileTensor/#copy_from_async)
provides a specialized asynchronous global-to-shared copy path with
backend-specific requirements. It is not a general replacement for synchronous
copies. Follow the backend's completion and synchronization requirements before
reading shared data.

For thread-aware copies, use
[`TileCopier`](/api/mojo/layout/tile_io/TileCopier/) to describe the partition
of work. See [Copying tensors](/tile-tensor/tensors/#copying-tensors) for native
copy examples and their GPU requirements.
