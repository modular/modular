When the built-in ops in MAX don't cover your computation (a specialized
activation, a fused operation, or a domain-specific kernel), you can write your
own in Mojo and call it from Python. In this tutorial, you'll learn to write
custom operations (ops) in Mojo that run on GPUs and CPUs, then declare them
in Python with `custom_op.declare()`. You'll call a declared op on eager
tensors and inside a graph.

We'll start with a custom op that adds `1` to every element in the graph's
input tensor, using an API that handles CPU and GPU device management. Then
you'll write specialized functions for CPUs and GPUs. GPU functions that run in
parallel are also known as _kernels_.

This page assumes a basic understanding of MAX graphs, which
are computation graphs written in Python. These graphs are the foundation for
high-performance AI models that run on MAX. To learn more, see [build a model
graph with Module](/develop/modules/). It also helps to know the [Mojo
language basics](https://mojolang.org/docs/manual/basics).

## Example 1: An elementwise add op

To learn how to create a custom op, let's look at a simple "hello world" example
that adds `1` to each element of a tensor, in parallel on a GPU when one is
available.

### Define the custom op in Mojo

Take a look at the custom op defined in
[`custom_ops/kernels/add_one.mojo`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/kernels/add_one.mojo).
You'll see a Mojo [struct](https://mojolang.org/docs/manual/structs) called
`AddOne` with an `execute()` function. A custom op defines either an `execute()`
function or an `elementwise()` method.
[Write a fusible elementwise op](#write-a-fusible-elementwise-op) covers the
second.

Depending on the purpose of your custom op, the `execute()` function accepts
zero or more inputs and produces one or more outputs, as specified by the
function arguments.

Let's inspect the struct and function signatures:

```mojo title="kernels/add_one.mojo"
@extensibility.register("add_one")
struct AddOne:
    @staticmethod
    def execute(
        output: Some[Output & Tensor],
        x: Some[Input & Tensor],
        ctx: DeviceContext,
    ) raises:
        # See below for the rest
```

The struct must include the
[`@extensibility.register()`](/api/mojo/extensibility/decorators/register/)
decorator, which registers the custom op with MAX. The `add_one` name set here
is the name we'll use to call the op from Python.

The rest of the `execute()` signature describes the custom op's graph node to
the graph compiler: the parameters, inputs, and outputs. The `execute()`
function must take `output` as the first runtime argument; the graph compiler
uses this order to identify the op's output slots:

- This op has no [compile-time
parameters](https://mojolang.org/docs/manual/parameters/#parameters-and-generics).
An op declares them when it needs values fixed at compile time, as later
examples do. The kind of hardware the function is compiled for comes from the
`ctx` argument instead (we'll use it in the next example).

- The runtime arguments are the op's inputs and outputs. Each argument's type
is a generic parameter bounded by
[tensor traits](/api/mojo/extensibility/tensor_arg_traits/): `Input` or
`Output` marks its role, and
[`Tensor`](/api/mojo/extensibility/tensor_arg_traits/Tensor/) exposes its
dtype, rank, and shape. `Some[Output & Tensor]` is shorthand for declaring that
parameter inline, the same as writing `[O: Output & Tensor](output: O)`. The
graph compiler supplies the concrete tensor type for each argument, whose memory
is managed outside of the operation.

Now let's look at the body of the `execute()` function. It adds `1` to each
element inside the `elementwise_add_one()` closure.

```mojo title="kernels/add_one.mojo" {9-31}
@extensibility.register("add_one")
struct AddOne:
    @staticmethod
    def execute(
        output: Some[Output & Tensor],
        x: Some[Input & Tensor],
        ctx: DeviceContext,
    ) raises:
        comptime assert conforms_to(type_of(output), TileTensorable)
        comptime assert conforms_to(type_of(x), TileTensorable)
        comptime dtype = type_of(output).dtype
        comptime output_alignment = type_of(output).alignment
        comptime assert type_of(x).rank == type_of(output).rank
        var output_tile = output.to_tile_tensor[dtype]()
        var x_tile = x.to_tile_tensor[dtype]().as_imm()

        @inline(.always)
        def elementwise_add_one[
            width: Int, alignment: Int = 1
        ](idx: Coord) {var}:
            var result = (
                x_tile.load[width=width, alignment=align_of[dtype]()](idx) + 1
            )
            output_tile.store[
                width=width,
                alignment=min(output_alignment, alignment * align_of[dtype]()),
            ](idx, result)

        elementwise[simd_width=get_kernel_simd_width[dtype, ctx.target]()](
            elementwise_add_one, output.shape(), ctx
        )
```

The body first checks that both arguments conform to
[`TileTensorable`](/api/mojo/extensibility/tensor_arg_traits/TileTensorable/),
then projects each one to a
[`TileTensor`](/api/mojo/layout/tile_tensor/TileTensor/) view over its memory
with `to_tile_tensor()`. The input's view is immutable (`as_imm()`).

We call `elementwise_add_one()` using
[`elementwise()`](/api/mojo/max/algorithm/functional/elementwise/),
which distributes an elementwise computation in parallel across all elements of
the output's shape. Each call loads and stores a SIMD vector of `width`
elements, and `alignment` tells the closure how far its index is aligned, in
elements. At compile time, `elementwise()` specializes the computation for the
device behind `ctx`, so the same code runs on CPU or GPU with no changes.

`get_kernel_simd_width()` picks the SIMD width for the device that
`ctx.target` names. The
[next example](#example-2-write-device-specific-kernels) branches on
`ctx.target` explicitly.

### Declare and call a custom op from Python

An op reaches Python through `custom_extensions`, which points at the Mojo
package directory that holds the kernels. The directory must contain an
`__init__.mojo` file, which can be empty, because MAX treats a directory as a
Mojo package only when the directory contains that file.

Declare the op once with
[`custom_op.declare()`](/api/python/generated/max.functional.custom_op.declare/),
then call it like a Python function. The declaration describes the op's
signature: the dtype and shape of each input and output. List the inputs in the
order that the kernel's `execute()` method takes them. The `inputs` keys, such
as `x` in the following example, name the inputs in error messages and let you
pass them as keyword arguments. They don't need to match the kernel's argument
names.

Each dimension in a shape is either a fixed size or a symbol that you create
with `custom_op.Symbols()`. A symbol stands for a size that each call fills in
from its arguments. When a symbol appears in more than one shape, it has the
same size everywhere in that call. In the following example, the input and the
output both use `rows` and `columns`, so the output always has the input's
shape, whatever shape the input has.

The
[`custom_ops/declared_addition.py`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/declared_addition.py)
example declares the `add_one` op, whose output has the same shape as its input:

```python title="declared_addition.py"
mojo_kernels = Path(__file__).parent / "kernels"

# The input and the output are matrices with the same shape.
rows, columns = custom_op.Symbols("rows", "columns")
add_one = custom_op.declare(
    "add_one",
    inputs={"x": custom_op.TemplateType(DType.float32, [rows, columns])},
    outputs=[custom_op.TemplateType(DType.float32, [rows, columns])],
    custom_extensions=[mojo_kernels],
)
```

`declare()` compiles the kernel package and checks that it registers the op.
It does this once, when you declare the op, and not on each call. Each call
checks its arguments against the declaration. An argument with the wrong dtype,
rank, or size raises an error that names the argument.

When you call the op on eager tensors, it runs on the tensors' device and
returns a `Tensor`:

```python title="declared_addition.py"
x = Tensor.from_dlpack(x_values).to(device)
result = add_one(x)
```

You can also use the declared op in a graph. The following code builds a graph
whose only op is `add_one`. `Graph()` calls the `forward` function once, with
the graph's input as a symbolic
[`TensorValue`](/api/python/generated/max.graph.TensorValue/) instead of a
tensor, and that call adds the `add_one` op to the graph. The op runs later,
each time you execute the compiled graph:

```python title="declared_addition.py"
device_ref = DeviceRef.from_device(device)
graph = Graph(
    "declared_addition",
    forward=add_one,
    input_types=[TensorType(DType.float32, ["m", "n"], device=device_ref)],
)
```

The input's shape, `["m", "n"]`, uses names instead of sizes, so the compiled
graph accepts a matrix with any number of rows and columns. These names belong
to the graph, not to the declaration. When `Graph()` calls `add_one`, the
declaration's `rows` and `columns` symbols take the graph's dimensions `m` and
`n`, and the op's output gets the same shape, `["m", "n"]`.

Run the example:

```sh
pixi run python declared_addition.py
```

A call must match its declaration:

- The declared shapes fix each input's rank. To accept inputs of another rank,
  declare the op again with shapes of that rank.
- A call doesn't broadcast its inputs. Each input must match its declared shape.
- All of a call's inputs must be on the same device. To combine tensors from
  different devices, move them with
  [`to()`](/api/python/generated/max.tensor.Tensor/#max.tensor.Tensor.to) first.
- A call takes either eager tensors or graph values, not a mix of both.

MAX allocates each output with its declared shape, and nothing checks that shape
against what the kernel writes. A declaration that understates an output's size
gives the kernel a smaller buffer than it expects. A kernel that sizes its loop
by the output returns a truncated result without an error, and one that sizes
it by an input can write past the buffer.

Inside a model, call a declared op from a layer's `forward()`, the same way as
in a graph. The module compiles the kernel into the model's graph.

### Call a custom op without declaring it

You can also call an op without a declaration by passing its output types with
each call. On eager tensors, use
[`F.custom()`](/api/python/functional/#max.functional.custom), as the
[`custom_ops/eager_vector_addition.py`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/eager_vector_addition.py)
example does:

```python title="eager_vector_addition.py"
mojo_kernels = Path(__file__).parent / "kernels"

vector_width = 10
dtype = DType.float32

# Place the op on a GPU, if available. Fall back to CPU if not.
device = CPU() if accelerator_count() == 0 else Accelerator()

lhs = random.uniform([vector_width], dtype=dtype, device=device)
rhs = random.uniform([vector_width], dtype=dtype, device=device)

result = F.custom(
    name="vector_addition",
    device=device,
    values=[lhs, rhs],
    out_types=[lhs.type],
    custom_extensions=mojo_kernels,
)[0]
```

`F.custom()` doesn't check dtypes or shapes against a declaration. The eager
interpreter runs only declared ops, so an undeclared op's eager call compiles a
graph first. That compile takes much longer than the op itself. MAX caches the
compiled graph and reuses it when a later call builds the same graph.

A model layer can wrap an `F.custom()` call the same way. The [custom layer
guide](/develop/layers/#wrap-a-custom-op) shows a layer that wraps a custom op.

### Add the custom op to a graph directly

In a graph that you build with `max.graph`, you can also add an undeclared op
with [`ops.custom()`](/api/python/graph.ops/#max.graph.ops.custom). The
[`custom_ops/addition.py`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/addition.py)
example does that. The path passed to `custom_extensions` takes one of two
forms:

- A Mojo package directory with an `__init__.mojo` file, as described in
  [Declare and call a custom op from Python](#declare-and-call-a-custom-op-from-python).
  MAX precompiles the directory each time it builds a graph or session, so it
  picks up your edits automatically. Use this form during development.
- A `.mojoc` file built with `mojo precompile`. Use this form to ship ops, and
  build it with the same Mojo version that the consumer runs.

A single `.mojo` file or a `.mojopkg` file is rejected. This example uses a
package directory:

```python title="addition.py"
mojo_kernels = Path(__file__).parent / "kernels"

rows = 5
columns = 10
dtype = DType.float32
device = CPU() if accelerator_count() == 0 else Accelerator()

graph = Graph(
    "addition",
    forward=lambda x: (
        ops.custom(
            name="add_one",
            device=DeviceRef.from_device(device),
            values=[x],
            out_types=[
                TensorType(
                    dtype=x.dtype,
                    shape=x.tensor.shape,
                    device=DeviceRef.from_device(device),
                )
            ],
        )[0].tensor
    ),
    input_types=[
        TensorType(
            dtype,
            shape=[rows, columns],
            device=DeviceRef.from_device(device),
        ),
    ],
    custom_extensions=[mojo_kernels],
)
```

The [`Graph()`](/api/python/generated/max.graph.Graph/) takes an input tensor
with five rows and ten columns, runs the custom `add_one` operation on it, and
returns the result.

That's the whole custom op: the graph now contains it and is ready to compile.

Now we can run an inference with
[`InferenceSession`](/api/python/generated/max.engine.InferenceSession/). First
we compile the graph for the selected `device`, either a CPU or GPU
"accelerator", then initialize it for execution:

```python title="addition.py"
session = InferenceSession(
    devices=[device],
)

compiled = session.compile(graph)
model = session.init(compiled)
```

Finally, we generate some random data and pass it as input:

```python title="addition.py"
# Fill an input matrix with random values.
x_values = np.random.uniform(size=(rows, columns)).astype(np.float32)

# Create a buffer and move it to the device (CPU or GPU).
x = Buffer.from_numpy(x_values).to(device)

# Run inference with the input tensor.
result = model.execute(x)[0]

# Copy values back to the CPU to be read.
assert isinstance(result, Buffer)
result = result.to(CPU())
```

The [`Buffer`](/api/python/generated/max.driver.Buffer/) is
initially resident on the host (CPU), so we move it to the accelerator before
use with the graph on that device. If the device is the host CPU and not an
accelerator, `to()` is a no-op. After the run, we move the result back to the
CPU to read it.

You can run this example as follows:

```sh
pixi run python addition.py
```

### Write a fusible elementwise op

The graph compiler can fuse an elementwise custom op with the ops around it. It
combines a chain of elementwise ops into one kernel, which skips writing each
intermediate tensor to memory and reading it back. It can also apply the chain
as the epilogue of a matmul that produces the chain's input.

To make an op fusible, define it with a static `elementwise()` method. The
method receives SIMD vectors of input values and returns a SIMD vector of
output values. The compiler handles loading, storing, and device dispatch.
The following op adds `1` to every element, like `add_one`:

```mojo title="kernels/add_one.mojo"
@extensibility.register("add_one_elementwise")
struct AddOneElementwise(ElementwiseUnaryOp):
    @staticmethod
    def elementwise[
        dtype: DType,
        width: SIMDLength,
    ](x: SIMD[dtype, width]) -> SIMD[dtype, width]:
        return x + 1
```

Declaring conformance to
[`ElementwiseUnaryOp`](/api/mojo/extensibility/operation_traits/ElementwiseUnaryOp/)
makes the compiler check the method signature. The
[operation traits](/api/mojo/extensibility/operation_traits/) module defines the
signatures for unary, binary, and comparison ops.

Add the op to a graph with `ops.custom()`, the same way as `add_one`. In
[`custom_ops/elementwise_addition.py`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/elementwise_addition.py),
the op and a multiply follow a matmul, so the compiler can apply both as the
matmul's epilogue:

```python title="elementwise_addition.py"
def add_one(x: TensorValue, device_ref: DeviceRef) -> TensorValue:
    return ops.custom(
        name="add_one_elementwise",
        device=device_ref,
        values=[x],
        out_types=[TensorType(dtype=x.dtype, shape=x.shape, device=device_ref)],
    )[0].tensor


def main() -> None:
    # ...
    graph = Graph(
        "elementwise_addition",
        forward=lambda a, b: add_one(a @ b, device_ref) * 2,
        input_types=[
            TensorType(dtype, shape=[rows, inner], device=device_ref),
            TensorType(dtype, shape=[inner, columns], device=device_ref),
        ],
        custom_extensions=[mojo_kernels],
    )
```

Run it the same way as the first example:

```sh
pixi run python elementwise_addition.py
```

An op that defines `execute()` with `Input` and `Output` tensor arguments runs
as its own kernel, including when it uses `elementwise()`. Use `execute()` when
an output element depends on input elements at other positions, or when the op
needs control over device dispatch.

## Example 2: Write device-specific kernels

[`elementwise()`](/api/mojo/max/algorithm/functional/elementwise/)
is a device-independent abstraction for elementwise computation: it handles
hardware dispatch and covers a range of CPUs and GPUs. The `add_one` custom op
uses it to run its computation. When you need direct control over thread
dispatch, block sizes, or GPU-specific memory patterns, write separate code
paths for CPU and GPU with Mojo's `comptime if` and the GPU thread model.

So let's now look at the
[`vector_addition.mojo`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/kernels/vector_addition.mojo)
custom op, which adds two vectors in parallel on a GPU.

This example uses a programming model that may be familiar if you've used
general purpose GPU programming in CUDA or similar frameworks: we're going to
write separate functions for GPUs and CPUs, and the GPU function (kernel) is
written specifically for parallelism across GPU threads.

The vector addition op in `kernels/vector_addition.mojo` looks like this:

```mojo title="kernels/vector_addition.mojo"
@extensibility.register("vector_addition")
struct VectorAddition:
    @staticmethod
    def execute(
        output: Some[Output & Tensor],
        lhs: Some[Input & Tensor],
        rhs: Some[Input & Tensor],
        ctx: DeviceContext,
    ) raises:
        comptime assert conforms_to(type_of(output), TileTensorable)
        comptime assert conforms_to(type_of(lhs), TileTensorable)
        comptime assert conforms_to(type_of(rhs), TileTensorable)
        comptime dtype = type_of(output).dtype
        comptime assert type_of(output).rank == 1
        comptime assert type_of(lhs).rank == 1
        comptime assert type_of(rhs).rank == 1
        var output_tile = output.to_tile_tensor[dtype]()
        var lhs_tile = lhs.to_tile_tensor[dtype]().as_imm()
        var rhs_tile = rhs.to_tile_tensor[dtype]().as_imm()

        comptime if ctx.target.is_cpu():
            _vector_addition_cpu(output_tile, lhs_tile, rhs_tile, ctx)
        elif ctx.target.is_gpu():
            _vector_addition_gpu(output_tile, lhs_tile, rhs_tile, ctx)
        else:
            raise Error("No known target:", ctx.target.device_kind_label())
```

Using the
[`comptime if`](https://mojolang.org/docs/manual/metaprogramming/comptime-evaluation/#comptime-if)
statement, Mojo checks at compile time if the target device has a GPU or not. If
it does, it uses the `_vector_addition_gpu()` function; otherwise, it uses
`_vector_addition_cpu()`. `comptime if` resolves that branch at compile time, so
the CPU build contains no GPU code.

The `_vector_addition_gpu()` function looks like this:

```mojo title="kernels/vector_addition.mojo"
def _vector_addition_gpu(
    output: TileTensor[mut=True, ...],
    lhs: TileTensor[output.dtype, ...],
    rhs: TileTensor[output.dtype, ...],
    ctx: DeviceContext,
) raises:
    comptime BLOCK_SIZE = 16
    var vector_length = Int(output.dim[0]())
    var length_dev = Int32(vector_length)

    def vector_addition_gpu_kernel() {var output, var lhs, var rhs, var length_dev}:
        var length = Int(length_dev)
        var tid = block_dim.x * block_idx.x + thread_idx.x
        if tid < length:
            var result = lhs.load[width=1](Coord(tid)) + rhs.load[width=1](
                Coord(tid)
            )
            output.store[width=1](Coord(tid), result)

    var num_blocks = ceildiv(vector_length, BLOCK_SIZE)
    ctx.enqueue_closure(
        vector_addition_gpu_kernel, grid_dim=num_blocks, block_dim=BLOCK_SIZE
    )
```

The `vector_addition_gpu_kernel()` closure runs once per thread on the GPU,
adding an element from the `lhs` vector to the matching element in the `rhs`
vector and then saving the result at the correct position in the `output`
vector. The closure copies the tensors and the length into its captures
(`{var ...}`), so `enqueue_closure()` can launch the closure itself as the
kernel across a grid of `BLOCK_SIZE` blocks of threads.

`BLOCK_SIZE` is untuned for this device. `elementwise()` picks the launch
parameters for the target and is the better choice for a simple elementwise op.
This kernel shows the thread-level mapping that `elementwise()` hides.

You can execute this one in the same manner as the previous example, by running
the Python-based graph that uses the custom op:

```sh
pixi run python vector_addition.py
```

### Register a kernel per platform

Instead of branching on `ctx.target` inside one kernel, you can register a
separate kernel for each platform. Pass a platform as the second argument to
`@extensibility.register()`. The `vector_addition.mojo` file also registers
a second op, `vector_addition_by_platform`, with one struct for CPUs and one
for accelerators:

```mojo title="kernels/vector_addition.mojo"
@extensibility.register("vector_addition_by_platform", CPU)
struct VectorAdditionCPU:
    @staticmethod
    def execute(
        output: Some[Output & Tensor],
        lhs: Some[Input & Tensor],
        rhs: Some[Input & Tensor],
        ctx: DeviceContext,
    ):
        comptime assert conforms_to(type_of(output), TileTensorable)
        comptime assert conforms_to(type_of(lhs), TileTensorable)
        comptime assert conforms_to(type_of(rhs), TileTensorable)
        comptime dtype = type_of(output).dtype
        _vector_addition_cpu(
            output.to_tile_tensor[dtype](),
            lhs.to_tile_tensor[dtype]().as_imm(),
            rhs.to_tile_tensor[dtype]().as_imm(),
            ctx,
        )


@extensibility.register("vector_addition_by_platform", ACCELERATOR)
struct VectorAdditionAccelerator:
    @staticmethod
    def execute(
        output: Some[Output & Tensor],
        lhs: Some[Input & Tensor],
        rhs: Some[Input & Tensor],
        ctx: DeviceContext,
    ) raises:
        # Same as VectorAdditionCPU, but calls _vector_addition_gpu().
```

When it compiles the op for a device, the graph compiler keeps the
registrations whose platform includes that device. You import `CPU` and
`ACCELERATOR` from `extensibility`, along with `CUDA`, `HIP`, and `METAL`,
which narrow an accelerator to one GPU API. If more than one registration
matches, the narrowest platform wins, so a kernel registered for `CUDA`
replaces the `ACCELERATOR` kernel on NVIDIA GPUs. If no platform is narrower
than all the others, the graph compiler reports an ambiguity error. The
[`register()`](/api/mojo/extensibility/decorators/register/) reference covers
the selection rules and how to build narrower platforms with `arch()` and
`model()`.

The `vector_addition.py` example runs both `vector_addition` and
`vector_addition_by_platform` on the CPU, and on a GPU when one is present.

The
[`custom_ops/declared_vector_addition.py`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/declared_vector_addition.py)
example declares `vector_addition` the same way that `declared_addition.py`
declares `add_one`. Both inputs and the output use one symbol, `n`, so a call
must pass two vectors of the same length:

```python title="declared_vector_addition.py"
(n,) = custom_op.Symbols("n")
vector_addition = custom_op.declare(
    "vector_addition",
    inputs={
        "lhs": custom_op.TemplateType(DType.float32, [n]),
        "rhs": custom_op.TemplateType(DType.float32, [n]),
    },
    outputs=[custom_op.TemplateType(DType.float32, [n])],
    custom_extensions=[mojo_kernels],
)
```

### Declare the output shape

Most ops get their output shapes from their inputs. The `add_one` output has its
input's shape, and the `vector_addition` declaration sizes its output with the
same symbol, `n`, as its inputs. When an output's size depends on the values in
an input, no input dimension determines it. The kernel must then register a
shape function with
[`@extensibility.register_shape_function()`](/api/mojo/extensibility/decorators/register_shape_function/),
which MAX runs on the host to compute the output shape before it runs the op.

The `keep_positive` op in
[`custom_ops/kernels/keep_positive.mojo`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/kernels/keep_positive.mojo)
returns the positive values of a vector, so its output length depends on the
input's values. Its shape function counts them:

```mojo title="kernels/keep_positive.mojo"
@extensibility.register_shape_function("keep_positive")
def keep_positive_shape(x: Some[TileTensorable]) raises -> IndexList[1]:
    var x_tile = x.to_tile_tensor()
    var length = coord_to_index_list(x.shape())[0]
    var count = 0
    for i in range(length):
        if x_tile[i] > 0:
            count += 1
    return IndexList[1](count)
```

The declaration in
[`custom_ops/keep_positive.py`](https://github.com/modular/modular/tree/main/max/examples/custom_ops/keep_positive.py)
sizes the output with a symbol, `k`, that no input uses:

```python title="keep_positive.py"
# No input binds k, so the kernel's shape function computes it at run time.
n, k = custom_op.Symbols("n", "k")
keep_positive = custom_op.declare(
    "keep_positive",
    inputs={"x": custom_op.TemplateType(DType.float32, [n])},
    outputs=[custom_op.TemplateType(DType.float32, [k])],
    custom_extensions=[mojo_kernels],
)
```

If the kernel doesn't register a shape function for an output whose size no
input binds, `declare()` raises an error. An op whose output shapes come from
its inputs doesn't need a shape function.

Shape functions must use tensor traits for tensor arguments. A shape function
that reads only an input's shape takes it as `Some[Tensor]`, which exposes a
tensor's shape, rank, and dtype but not its elements. If it reads element
values, as `keep_positive_shape()` does, use `Some[TileTensorable]` and access
them through `to_tile_tensor()`. For variadic inputs, use a
[`TensorTuple`](/api/mojo/extensibility/tensor_tuple/TensorTuple/) whose
elements bind the traits they need. Shape functions reject the
`ManagedTensorSlice` and `VariadicTensors` types and their aliases, such as
`InputTensor` and `InputVariadicTensors`.

For an op on a GPU, MAX copies each tensor input not bound to `Some[Tensor]` to
the host before the shape function runs, and the host waits for the copy. Use
`Some[Tensor]` for inputs whose elements the shape function doesn't read.

The `keep_positive` kernel is a serial loop, so it registers for the `CPU`
platform only, and the example keeps its input on the CPU. Run the example:

```sh
pixi run python keep_positive.py
```

## Choose how to call and dispatch an op

You wrote custom ops and called them from Python:

- `AddOne`, which uses `elementwise()` for automatic device dispatch
- `AddOneElementwise`, which the graph compiler can fuse with neighboring ops
- `VectorAddition`, which uses `comptime if` to dispatch separate CPU and GPU
  implementations
- `VectorAdditionCPU` and `VectorAdditionAccelerator`, which register separate
  CPU and GPU kernels for one op

To call an op from Python, declare it with `custom_op.declare()` when you know
the rank of each input. A declared op checks every call against its signature,
and MAX can run its eager calls without compiling a graph. A declaration fixes
each input's rank, so for an op that must accept inputs of several ranks, use
`F.custom()` on eager tensors or `ops.custom()` in a graph.

Define `elementwise()` for elementwise ops you want the compiler to fuse. Use
`elementwise()` inside `execute()` for other ops where device-specific tuning
isn't needed. Write device-specific kernels when you need direct control over
thread layout and memory access patterns. Branch on `ctx.target` with
`comptime if` when the CPU and GPU code paths share their setup. Register a
kernel per platform when the paths are separate kernels, or to add a kernel for
one GPU API without changing the others.

## Fix kernel registration errors

When you write your own kernels, a mistake in a kernel's signature stops MAX
from loading its package. MAX checks the kernels in a package when it loads the
package, such as when `declare()` resolves an op. If a kernel's signature breaks
a registration rule, MAX raises
[`KernelRegistrationError`](/api/python/generated/max.graph.KernelRegistrationError/)
with the Mojo file, line, and column of the problem.

For example, swap the `output` and `x` arguments of `AddOne.execute()` in
`kernels/add_one.mojo`, then run `declared_addition.py`. MAX raises this
error:

```output
max.graph.KernelRegistrationError:
.../kernels/add_one.mojo:40:9: error: Outputs must appear before inputs in the function signature: output 'output' comes after input 'x'
        output: Some[Output & Tensor],
        ^
```

To fix it, list the outputs first, then the inputs, and put the
[`DeviceContext`](/api/mojo/max/gpu/host/device_context/DeviceContext/) last:

```mojo title="kernels/add_one.mojo"
def execute(
    output: Some[Output & Tensor],
    x: Some[Input & Tensor],
    ctx: DeviceContext,
) raises:
```
