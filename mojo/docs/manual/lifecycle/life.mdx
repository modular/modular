The life of a value in Mojo begins when you initialize a variable and continues
up until the value's last use, at which point Mojo destroys it. This page
describes how Mojo creates, copies, and moves every value. (The next
page describes [how values are
destroyed](/docs/manual/lifecycle/death).)

Mojo defines all data types—including basic types in the standard library such
as [`Bool`](/docs/std/builtin/bool/Bool/), [`Int`](/docs/std/builtin/simd/#int),
and [`String`](/docs/std/collections/string/string/String/)—as
[structs](/docs/manual/structs/). This means the creation and destruction of any
piece of data follows the same lifecycle rules, and you can define your own data
types that work exactly the same way.

Mojo structs don't get any default lifecycle methods, such as a
a initializer, copy initializer, or move initializer. That means you can define
a struct without a initializer, but then you can't instantiate it, and it
would be useful only as a sort of namespace for static methods. For example:

```mojo
struct NoInstances:
    var state: Int

    @staticmethod
    def print_hello():
        print("Hello world!")
```

Without an initializer, this can't be instantiated, so it has no lifecycle.
The `state` field is also useless because it can't be initialized (Mojo
structs do not support default field values—you must initialize them in an
initializer).

So the only thing you can do is call the static method:

```mojo
NoInstances.print_hello()
```

```output
Hello world!
```

## initializer {#constructor}

To create an instance of a Mojo type, it needs the `__init__()` initializer
method. The main responsibility of the initializer is to initialize all fields.
For example:

```mojo
struct MyPet:
    var name: String
    var age: Int

    def __init__(out self, name: String, age: Int):
        self.name = name
        self.age = age
```

Now we can create an instance:

```mojo
var mine = MyPet("Loki", 4)
```

You can also read and destroy an instance of `MyPet`, but you currently can't
copy or move it.

We believe this is a good default starting point, because there are no built-in
lifecycle events and no surprise behaviors. You—the type author—must
explicitly decide whether and how the type can be copied or moved, by
implementing the copy and move initializers.

The pattern shown above is an initializer that takes an argument for each
of the struct's fields and initializes the fields directly from the
arguments. It's called a *field-wise initializer*. It's a common enough
pattern that Mojo includes a
[`@fieldwise_init`](/docs/reference/decorators/fieldwise-init/) decorator
to synthesize the field-wise initializer. So you can rewrite the previous
example like this:

```mojo
@fieldwise_init
struct MyPet:
    var name: String
    var age: Int
```

:::note

Mojo doesn't require a destructor to destroy an instance. But in some cases,
you may need to define a custom destructor to release resources (for example, if
a struct dynamically allocates memory using
[`alloc()`](/docs/std/memory/alloc/alloc/)). We'll
discuss that more in [Death of a value](/docs/manual/lifecycle/death/).

:::

:::note The "initializer" name

In a Python class, object construction happens across both the `__new__()` and
`__init__()` methods, so the `__init__()` method is technically just the
initializer for attributes (but it's often still called the constructor).
However, in a Mojo struct, there is no `__new__()` method, so we prefer to
always call `__init__()` the initializer.

:::

### Overloading the initializer {#overloading-the-constructor}

Like any other function/method, you can
[overload](/docs/manual/functions/#overloaded-functions) the
`__init__()` to initialize the object with different arguments. For
example, you might want a default initializer that sets some default values and
takes no arguments, and then additional initializers that accept more arguments.

Just be aware that, in order to modify any fields, each initializer must
declare the `self` argument with the [`out`
convention](/docs/manual/values/ownership#argument-conventions). If you
want to call one initializer from another, you simply call upon that
initializer as you would externally (you don't need to pass `self`).

For example, here's how you can delegate work from an overloaded initializer:

```mojo
struct MyPet:
    var name: String
    var age: Int

    def __init__(out self):
        self.name = ""
        self.age = 0

    def __init__(out self, name: String):
        self = MyPet()
        self.name = name
```

### Field initialization

Notice in the previous example that, by the end of each initializer, all
fields must be initialized. That's the only requirement in the initializer.

In fact, the `__init__()` initializer is smart enough to treat the `self`
object as fully initialized even before the initializer is finished, as
long as all fields are initialized. For example, this initializer can pass
around `self` as soon as all fields are initialized:

```mojo
def use(arg: MyPet):
    pass

struct MyPet:
    var name: String
    var age: Int

    def __init__(out self, name: String, age: Int, cond: Bool):
        self.name = name
        if cond:
            self.age = age
            use(self)  # Safe to use immediately!

        self.age = age
        use(self)  # Safe to use immediately!
```

### Initializers and implicit conversion {#constructors-and-implicit-conversion}

Mojo supports implicit conversion from one type to another. Implicit conversion
can happen when one of the following occurs:

- You assign a value of one type to a variable with a different type.
- You pass a value of one type to a function that requires a different type.
- You return a value of one type from a function that specifies a different
  return type.

For example, the [`Optional[T]`](/docs/std/collections/optional/Optional/) type
models a value that may or may not be present. You can implicitly convert a
value of type `T` into an `Optional[T]`, and you can implicitly convert a value
of `None` into an empty `Optional[T]`:

```mojo
var opt_greeting: Optional[String] = None  # implicitly converts to an empty Optional
opt_greeting = String("Salve!")  # implicitly converts the String into an Optional
```

In general, types should only support implicit conversions when the conversion
is:

- Safe
- Zero-cost or low-cost
- Semantically unambiguous

Implicit conversion exists to reduce unnecessary boilerplate, not to
weaken type safety.

#### Enabling implicit conversion

Mojo supports implicit conversion only when the target type defines
an initializer that meets the following criteria:

- Has the [`@implicit`](/docs/reference/decorators/implicit/) decorator.
- Has a single required, non-keyword argument of the source type.

For example:

```mojo
var a = Source()
var b: Target = a
```

Mojo implicitly converts the `Source` value in `a` to a `Target` value if
`Target` defines a matching initializer like this:

```mojo
struct Target:

    @implicit
    def __init__(out self, s: Source):
        pass
```

With implicit conversion, the assignment above is essentially identical to
using the initializer:

```mojo
var b = Target(a)
```

The initializer used for implicit conversion can take optional arguments, so
the following initializer would also support implicit conversion from `Source`
to `Target`:

```mojo
struct Target:

    @implicit
    def __init__(out self, s: Source, reverse: Bool = False): ...
```

Implicit conversion can fail if Mojo can't unambiguously match the conversion to
an initializer. For example, if the target type has two overloaded initializers
that take different types, and each of those types supports an implicit
conversion from the source type, the compiler has two equally-valid paths to
convert the values:

```mojo
struct A:
    @implicit
    def __init__(out self, s: Source): ...

struct B:
    @implicit
    def __init__(out self, s: Source): ...

struct OverloadedTarget:
    @implicit
    def __init__(out self, a: A): ...
    @implicit
    def __init__(out self, b: B): ...

var t = OverloadedTarget(Source()) # Error: ambiguous call to '__init__': each
                                   # candidate requires 1 implicit conversion
```

In this case, you can fix the issue by explicitly casting to one of the
intermediate types. For example:

```mojo
var t = OverloadedTarget(A(Source())) # OK
```

Mojo applies at most one implicit conversion to a variable. For example:

```mojo
var t: OverloadedTarget = Source() # Error: can't implicitly convert Source
                                   # to Target
```

This fails because there's no direct conversion from `Source` to
`OverloadedTarget`.

For structs with a single field, you can generate an implicit initializer with
the `@fieldwise_init("implicit")` decorator.

```mojo
@fieldwise_init("implicit")
struct Counter:
    var count: Int

def main():
    var c: Counter = 5  # implicitly converts from Int
```

## Copy initializer {#copy-constructor}

In Mojo, you can copy a value either *explicitly* or *implicitly*:

```mojo
# Explicit copy
var s = "Test string"
var s2 = s.copy()

# Implicit copy
var i = 15
var i2 = i
```

To make a struct explicitly copyable, you need to:

- Add the `Copyable` trait.
- (Optionally) define a custom copy initializer if needed, written
  `def __init__(out self, *, copy: Self)`.

By adding the `Copyable` trait, Mojo can generate a default
copy initializer for you unless you've written one yourself.
This default method copies each field of the copied value
into the new value. The `Copyable` trait also defines a default
`copy()` method which provides an additional way to copy a value,
versus calling the copy initializer directly:

```mojo
@fieldwise_init
struct MyPet(Copyable):
    var name: String
    var age: Int
```

Now this code works to make a copy:

```mojo
var mine = MyPet("Loki", 4)
var yours = mine.copy()
```

:::note
Technically, you *could* make a struct with a copy initializer and *not*
add the `Copyable` trait, but this isn't recommended. Mojo would be able
to copy the value, but you couldn't use the struct with any parameterized
containers or functions that require the `Copyable` trait.
:::

The generated copy initializer simply copies each field from the existing value
into the new value. For example, if you manually wrote the copy initializer for
`MyPet`, it would look like this:

```mojo
def __init__(out self, *, copy: Self):
    self.name = copy.name
    self.age = copy.age
```

This default copy initializer works in most cases, but there are a few cases
where you need to define a custom copy initializer:

- One or more of the struct's fields aren't `Copyable`.
- The struct includes a non-owning type (like
  [`Pointer`](/docs/std/memory/pointer/Pointer/)), and you
  want to make a deep copy of the data.
- The struct holds other resources (like file descriptors or network sockets)
  that you need to manage.

### Custom copy initializer {#custom-copy-constructor}

What makes Mojo's copy behavior different, compared to other languages, is
that copy initializer is designed to perform a deep copy of all fields in
the type (as per [value semantics](/docs/manual/values/value-semantics/)).
That is, it copies heap-allocated values, rather than just copying the
pointer.

However, the Mojo compiler doesn't enforce this, so it's the type author's
responsibility to implement a copy initializer with value semantics.

For example, here's a new `HeapArray` type with a custom copy initializer that
performs a deep copy:

```mojo
from std.memory import alloc, dealloc, ThinAllocation

struct HeapArray(Copyable, Writable):
    var data: ThinAllocation[Int]
    var size: Int
    var cap: Int

    def __init__(out self, size: Int, val: Int):
        self.size = size
        self.cap = size * 2
        self.data = alloc[Int]({count = self.cap}).into_thin()
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            ptr.unsafe_offset(i).unsafe_write(val)

    def __init__(out self, *, copy: Self):
        # Deep-copy the existing value
        self.size = copy.size
        self.cap = copy.cap
        self.data = alloc[Int]({count = self.cap}).into_thin()
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            var copy_ptr = copy.data.unsafe_ptr()
            ptr.unsafe_offset(i).unsafe_write(copy_ptr[unsafe_offset=i])
        # The lifetime of `copy` continues unchanged

    def __deinit__(deinit self):
        # We must free the heap-allocated data, but
        # Mojo knows how to destroy the other fields
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            ptr.unsafe_offset(i).unsafe_deinit_pointee()
        dealloc(
            self.data^.unsafe_with_layout({count = self.cap})
        )

    def append(mut self, val: Int):
        # Update the array for demo purposes
        if self.size < self.cap:
            var ptr = self.data.unsafe_ptr()
            ptr.unsafe_offset(self.size).unsafe_write(val)
            self.size += 1
        else:
            print("Out of bounds")

    def write_to(self, mut writer: Some[Writer]):
        writer.write("[")
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            writer.write(ptr[unsafe_offset=i])
            if i < self.size - 1:
                writer.write(", ")
        writer.write("]")
```

Notice that the copy initializer doesn't copy the `UnsafePointer` value
(doing so would make the copied value refer to the same `data` memory
address as the original value, which is a shallow copy). Instead,
initialize a new `UnsafePointer` to allocate a new block of memory, and
then copy over all the heap-allocated values (this is a deep copy).

When copying an instance of `HeapArray`, each copy has its own set of
values on the heap, so changes to one array don't affect the other, as
shown here:

```mojo
    var a = HeapArray(2, 1)
    var b = a.copy()  # Calls the copy method
    print(a)  # Prints [1, 1]
    print(b)  # Prints [1, 1]

    b.append(2)  # Changes the copied data
    print(b)   # Prints [1, 1, 2]
    print(a)   # Prints [1, 1] (the original did not change)
```

Two other things to note from the copy initializer:

- The `copy` argument is type `Self` (capital "S"). `Self` is an alias for
  the current type name (`HeapArray`, in this example). Using this alias is a
  best practice to avoid any mistakes when referring to the current struct name.

- The `copy` argument is immutable because the default [argument
  convention](/docs/manual/values/ownership#argument-conventions) is
  an immutable reference. This is a good thing because this function
  shouldn't modify the contents of the value it copies.

:::note

In `HeapArray`, we must use the `__deinit__()` destructor to free the
heap-allocated data when the `HeapArray` lifetime ends, but Mojo automatically
destroys all other fields when their respective lifetimes end. We'll discuss
this destructor more in [Death of a value](/docs/manual/lifecycle/death/).

:::

If your type doesn't use any pointers for heap-allocated data, then writing
the initializer and copy initializer is all boilerplate code that you
shouldn't have to write. For most structs that don't manage memory
explicitly, you can add the `Copyable` trait to your struct definition, and
Mojo will synthesize the copy initializer.

:::note
Mojo also calls upon the copy initializer when a value is passed to a
function that takes the argument as
[`var`](/docs/manual/values/ownership/#transfer-arguments-var-and-) *and*
when the lifetime of the given value does *not* end at that point. If the
lifetime of the value does end there (usually indicated with the transfer
sigil `^`), then Mojo instead invokes the move initializer.
:::

### Non-owning types

The default expectation in Mojo is that copying a value yields an
independent value—a deep copy.

Sometimes, though, it's more efficient for a struct to *avoid* copying data.
[`Span`](/docs/std/collections/span/Span/) and
[`StringSpan`](/docs/std/collections/string/string_span/StringSpan/) are
examples of *non-owning types* that hold pointers to underlying data they don't
own.

When you copy a non-owning type, it typically copies the *pointer*, leaving
both the original and the copy pointing to the same data.

A `StringSpan` represents a non-owning view of contiguous string data. Using
`StringSpan` when manipulating strings can be very efficient because it doesn't
copy the string data. For example, when using a slice operation to extract a
portion of a string, you get back a `StringSpan` that refers to the original
string's data. The actual `StringSpan` doesn't need to copy any of the string
data: it only holds a pointer to the beginning of the substring, and the length
of the substring.

Mojo makes it easy to build non-owning types like `StringSpan` by writing custom
constructors and copy constructors. Because Mojo types normally own their
data, you should clearly document any non-owning types, or any methods that
return non-owning views.

### Implicitly-copyable types

To make a type *implicitly copyable*, add the
[`ImplicitlyCopyable`](/docs/std/traits/copyable/ImplicitlyCopyable/) trait:

```mojo
@fieldwise_init
struct MyPair(ImplicitlyCopyable):
    var first: Int
    var second: Int

def main():
    var pair = MyPair(3, 4)
    var copy = pair
    print(pair.first, copy.second)
```

The `ImplicitlyCopyable` trait refines `Copyable`, so adding
`ImplicitlyCopyable` to your type gives you `Copyable`'s copy
initializer and a `copy()` method. It also gives you automatic
`Movable` conformance.

The trait doesn't define any methods of its own: it serves as a signal
to the compiler that it can insert calls to copy initializer as needed. For
example, in the previous example, the compiler might generate code equivalent
to:

```mojo
var pair = MyPair(3, 4)
var copy = pair.copy()
```

A type should be implicitly copyable only if copying the type is inexpensive and
has no side effects. Unnecessary copies can be a big drain on memory and
performance, so use this trait with caution.

In particular, any type that dynamically allocates memory or manages other
resources probably shouldn't be implicitly copyable.

## Move initializer {#move-constructor}

Although copying values provides predictable behavior that matches Mojo's
[value semantics](/docs/manual/values/value-semantics/), copying some data
types can be a significant hit on performance.

Mojo uses the move initializer to transfer ownership of a value from one
variable to another, *without* copying its fields. A value that's copyable
but doesn't have a move initializer can still be transferred by making a copy
and then discarding the original. So in this case, the move initializer serves
as an optimization.

To make a type *movable*:

- Add the `Movable` trait *or* conform to `Copyable`.
- (Optionally) implement a custom move initializer.

Here's a movable (also copyable) version of the `MyPet` struct:

```mojo
@fieldwise_init
struct MyPet(Copyable):
    var name: String
    var age: Int
```

Here's an example showing how to invoke the move initializer for `MyPet`:

```mojo
def moves():
    var a = MyPet("Bobo", 2)

    print(a.name) # Prints "bobo"

    var b = a^ # the lifetime of `a` ends here

    print(b.name) # prints "bobo"
    # print(a.name)  # ERROR: use of uninitialized value 'a'
```

If you include the `Movable` trait and don't define a move initializer, Mojo
generates a default move initializer for you. This move initializer simply
moves each of the fields to the new instance.

The generated move initializer for `MyPet` would look like this if you wrote
it yourself:

```mojo
def __init__(out self, *, deinit move: Self):  # move initializer
    self.name = move.name^
    self.age = move.age
```

The move initializer takes its `move` argument using the `deinit`
[argument convention](/docs/manual/values/ownership/#argument-conventions),
which grants exclusive ownership of the value and marks it as destroyed at the
end of the function. (For more information on the `deinit` convention, see
[Field lifetimes during destruct and move](/docs/manual/lifecycle/death/#field-lifetimes-during-destruct-and-move).)

The move initializer uses the transfer sigil (`^`) to indicate that
ownership of the `name` value transfers from `move` to `self`. For
trivial register-passable types like `Int`, omit the transfer sigil.
Trivial types are always movable. Since they can't define custom move
initializers or destructors, there's no special logic required to move.

At the end of the move initializer method, Mojo immediately invalidates the
original variable, preventing any access to it. Because the argument is
declared as `deinit`, it does *not* call the destructor, since that would
destroy resources that have been transferred to the new instance.
Invalidating the original variable is important to avoid memory errors on
heap-allocated data, such as use-after-free and double-free errors.

:::note
A move initializer is *not required* to transfer ownership of a
value. Mojo can copy the value and
invalidate the original instance. You can learn more in the section about
[ownership
transfer](/docs/manual/values/ownership#transfer-arguments-var-and-).

If copying a type is expensive, moving it with a move initializer is much
more efficient. For example, if a type has heap-allocated data, a copy
initializer typically needs to allocate new storage to make a deep copy of the
data.

For types without heap-allocated fields, you get no real benefit from the move
initializer. Making copies of simple data types on the stack, like integers,
floats, and booleans, is very cheap. Yet, if you allow your type to be copied,
then there's generally no reason to disallow moves.
:::

### Custom move initializer {#custom-move-constructor}

In practice, structs very rarely require a custom move initializer. A type might
require a custom implementation if it has a pointer to itself or one of its
fields, for example, since the struct's location in memory changes when it
moves.

The move initializer performs a consuming move: it [transfers
ownership](/docs/manual/values/ownership#transfer-arguments-var-and-) of a
value from one variable to another when the original variable's lifetime ends
(also called a "destructive move").

A critical feature of move initializers is that it takes the incoming value
as a `deinit` argument, meaning this method gets unique ownership of the
value. Moreover, because this is a dunder method that Mojo calls only when
performing a move (during ownership transfer), Mojo guarantees that the
`move` argument is a mutable reference to the original value, *not a copy*
(unlike other methods that may declare an argument as `var`, but might
receive the value as a copy if you call the method without the [`^`
transfer
sigil](/docs/manual/values/ownership/#transfer-arguments-var-and-)). That
is, Mojo calls this move initializer *only* when the original variable's
lifetime actually ends at the point of transfer.

## Move-only and immovable types

To prevent implicit copies of your type, you can make it "move-only" by
making it `Movable` but not `Copyable`. You can pass a move-only type
to other variables and into functions with any argument convention
(like `mut` or `var`). The only catch is that you must use the `^`
transfer sigil to end the lifetime of a move-only type when assigning it to a
new variable or when passing it as a `var` argument. The
[`OwnedPointer`](/docs/std/memory/owned_pointer/OwnedPointer/) is an
example of a move-only type: because it provides clear single
ownership of a stored value, you can move an `OwnedPointer`, but not copy it.

In some (rare) cases, you may not want a type to be copyable *or* movable. The
[`Atomic`](/docs/std/atomic/atomic/Atomic/) type is an example of a type that's
neither copyable nor movable.

### Trivial lifecycle methods

For many types, the lifecycle methods may be *trivial*, that is, they have
no custom behavior, and the compiler can replace or
eliminate calls to the methods, as described below:

- [`is_trivially_copyable()`](/docs/std/memory/memory/is_trivially_copyable/)
  returns true if a `Copyable` type is *trivially copyable*, which is an
  optimization hint that guarantees that copying the value's bits
  from one location to another causes no side effects.

- [`is_trivially_movable()`](/docs/std/memory/memory/is_trivially_movable/)
  returns true if a `Movable` type is *trivially movable*, which is an
  optimization hint that guarantees that moving the value's bits
  from one location to another causes no side effects.

- [`is_trivially_deletable()`](/docs/std/memory/memory/is_trivially_deletable/)
  returns true if a [`Deinitable`](/docs/std/traits/deinitable/Deinitable/) type
  is *trivially deinitable*, which is a hint that the `__deinit__()` method is
  a no-op and the compiler can skip it.
